# S2 查询构造与证据排序修复

本页记录查询修复的开发验收。后续 159 单元正式修订轮的预检、执行及中断恢复状态见[正式改进方案](rag_value_formal_revision.cn.md)。

正式运行的 S2 有 48 个适用单元，全部没有召回段落。运行后对固定实验库的只读诊断确认：16 份文档、8,820 个 chunk、FTS 内容及索引正常；39 个查询的布尔条件要求了不存在的词项，另外 9 个查询要求的词项未在同一 chunk 中共现。完整问题中的输出要求、快照描述和多对象名称成为了额外检索约束。

修复使用独立策略 `rag-value-lexical-query-v1`。原始正式运行及其 S0/S2 对照结果继续按原实现解释，参见[正式结果](rag_value_formal_results.cn.md)。

## 修复后的行为

- 从原问题提取有来源位置的实体、accession、DOI 或有限主题词，用 `plainto_tsquery` 构造查询。普通连字符写法统一；不猜测生物学别名，不读取参考答案或 Oracle。
- 把同一短语里的物种、菌株和基因关联为一个检索对象。不同对象分别召回、轮流进入最终证据，避免同一对象重复占用名额。
- 用各对象附近的题面词项对正文做软排序，包括问题已经给出的长度、位置及区域描述。它们不变成必须全部匹配的条件；上下文相关性优先，随后考虑文档多样性和实体匹配。
- accession 保留精确边界和版本；同一对象的宽泛物种名不能绕过未知 accession。DOI 保留精确文献约束。所有分支继续受固定语料和文档权限范围限制。
- 完整原问题继续用于模型提示词和 BGE 查询。输入预算、模型、温度、提示词和范围拒答规则沿用原配置。最多保存 100 个候选、提供 8 段证据。
- 查询规划、原文位置、PostgreSQL 规范化查询、各组命中数、对象候选及诊断校验值随运行记录保存。无候选明确记录 `no_chunks_retrieved`；无法规划和超出规划上限也有原因。

## 启用与复核

新运行配置需显式加入：

```json
{"lexical_query_policy": "rag-value-lexical-query-v1"}
```

省略该项继续使用 `original-question-v1`。新策略仅由来源报告实验适配器注入，影响 S2 的 FTS 和 S3/S5 的 FTS 分支；公共检索接口没有新增开关。

新配置必须绑定实际使用的全部实现文件，包含 `lexical_query.py`、`lexical_context.py`、`planned_fts.py`、`source_corpus.py`、`source_experiment.py` 和文献 `repository.py`。已有配置和批准记录不能通过修改一个字段直接沿用：重新冻结代码与配置，将输入采用记录绑定到新配置，再使用新的输出目录运行[正式入口](rag_value_source_runtime.cn.md)。这次修复没有启动新的 53 × 7 模型实验。

无需加载模型即可执行开发检索回归：

```sh
.venv/bin/python scripts/check_rag_value_lexical_retrieval.py \
  --config /absolute/path/to/pinned-data-config.json \
  --config-sha256 <data-config-sha256> \
  --cases /absolute/path/to/validation-cases.json \
  --cases-sha256 <validation-cases-sha256> \
  --output /absolute/path/to/new-validation-directory \
  --scan-questions
```

脚本核对题面、语料和验收规格的校验值，仅连接指定的本地只读实验库。预期文献与 chunk 只用于检索后的评分；检索器接收题面，不接收预期结果。运行前后核对实现文件，运行中代码发生变化则验收失败。原始文献、运行凭据和验收结果留在本地 `outputs/`，不随仓库分发。

## 验证范围

开发验收规格在第一次修复验证前冻结：12 个 Case，包括 9 个正例、1 个未知 accession 和 2 个范围拒答。正例既检查前 100 个候选，也检查模型实际可见的前 8 段；多对象题要求所有对象的指定事实来源均被覆盖。

第一轮有 10/12 个 Case 通过，VLE 及三对象问题未把关键段落排入前 8；失败记录保留，验收规格未放宽。后续排序据此改进，因此该组用例属于开发回归验收，不能作为独立泛化能力评测。

最终实际数据库复核为 **12/12 通过**。VLE 单对象题有 3 段指定事实证据进入前 8；三对象题的 GEVE、ERV、VLE 各有 2 段指定事实证据进入前 8。未知 accession 保持明确空结果，两个越界请求均先于检索拒答。

原 53 题的独立检索扫描得到 44 题有候选、5 题范围拒答、4 题无候选。UNSUP-05、UNSUP-09、UNSUP-13 因主题词超出规划上限而明确拒绝规划；UNSUP-06 使用主题词回退后没有匹配。题号不决定运行行为，也没有为了提高非空比例而放宽这些结果。该扫描不包含生成或专家评分，不能将 44/53 解释为答案正确率或充分证据覆盖率。

定向工程验证共 75 项通过，覆盖新查询与上下文规划、适配器、默认路径、融合和文档锚点。首次受沙箱连接限制跳过的 4 项 PostgreSQL 测试已在独立测试库补跑通过；不计为重复新增用例。相关文件的 Ruff 和 6 个实现文件的 mypy 检查通过。未重跑全仓 1,500 项，也未执行真实 S3/S5 的 BGE 加模型生成回归。

本地最终检索记录位于 `outputs/s2_repair_20260909/retrieval_validation_v2/`，规格校验值为 `d55c4c182508c68391c322b56780b6e08406df586ef6547d176f516133abcb7c`。这次查询脚本只读访问实验库；数据库集成测试单独使用测试库中的临时 schema。

工程检查用于确认查询、证据预算、范围隔离、版本绑定和失败记录按设计工作。检索有结果、指定文献进入证据包，均不等于模型回答科学正确；新策略的回答质量仍需独立正式运行与专家评分。
